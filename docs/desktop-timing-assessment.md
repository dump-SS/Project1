# 桌面端前移到 beta：影响评估与建议

> **性质**：决策**前置材料**（不是 ADR，尚未拍板），非契约、非行动依据。
> 日期：2026-09-22 · 触发：`pending-decisions.md` **#53**（原口径：2.0 = 桌面端 + agent harness）→ 现考虑把**桌面端前移到 beta**
> 相关：`refactor-development-plan.md`（M0–M6 / 阶段口径）· `ref-openmaic-harness-notes.md`（harness 底座调研）

---

## 0. 结论先行

**建议把「桌面端」拆成两件不同的事，只前移其中一件：**

| | 是什么 | 动什么 | 前移成本 | 建议 |
|---|---|---|---|---|
| **桌面端「壳」** | 把现有 Web 应用包成桌面应用 | 打包与分发；后端不变 | **低** | ✅ **可以前移到 beta** |
| **桌面端「harness」** | agent 循环跑在本地进程 | **架构**（#53 要求的 LLM/业务解耦） | **高** | ❌ **留在 2.0** |

**但有一个绕不过去的连锁**：桌面端的技术栈选择（Electron vs Tauri）**取决于 harness 最终在不在本地**，
而技术栈必须在 beta 就定死 —— 所以**「harness 最终在哪跑」这个问题被这个决定强行提前了**（见 §2）。
这是本次前移最真实、也最容易被忽略的代价。

---

## 1. 前移「壳」的连锁影响：现在就该做的 6 条约束

这些约束**今天做成本≈0，beta 再补成本高**。建议以「桌面端兼容性约束」为名，写进 X1 板块契约。

| # | 约束 | 为什么现在做 | 成本 |
|---|---|---|---|
| 1 | **X1 定义要从「前端壳与响应式」扩成「三端壳」**（Web / 移动 Web / 桌面） | M1 就有「X1 壳初版」在动工，**做完再改定义 = 返工** | 改文档 |
| 2 | **浏览器专有 API 要收进一个薄抽象层**：`localStorage`（主题 `epochx-theme`、收藏虚化状态）、`EventSource`（SSE）、剪贴板、文件选择 | Electron 与 Tauri 的 WebView 不同（Windows=WebView2、macOS=WKWebView）；散落直调会在打包时集中爆雷 | 小 |
| 3 | **SSE 必须带事件 id + 支持重连补发**（`Last-Event-ID`） | 桌面端会合盖休眠、切网。**这正好是 OpenMAIC durable session 要解决的问题**（见 harness 笔记 §3.2「live 与 replay 必须一致」） | 中（但 B 板块 M1 本来就在写 SSE） |
| 4 | **桌面端不得内嵌任何模型密钥，模型调用一律经服务端** | ✅ **天然满足** —— pilot 已要求 `usage_ledger` 挂在 LLM provider 出口（M1 硬前置）。写下来是为了防止 beta 被"本地跑模型省服务器"诱惑 | 0（只需声明） |
| 5 | **beta 桌面端明确不做本地持久化与离线** | 一旦本地存数据，就撞上未成年产品的「数据不出境 / 撤回即删除 / 监护人授权」；还会引入同步冲突。**先关掉这个选项，成本最低** | 0（只需声明） |
| 6 | **移动端与桌面端是两套断点体系，别混进同一套 `@media` 策略** | X1 现在只规划了「移动端响应式起步」（M2）。桌面端的约束是**窗口最小尺寸**，不是断点 | 小 |

---

## 2. ⚠️ 关键连锁：技术栈选择被「harness 在哪跑」绑死

桌面端技术栈必须在 beta 定，而两个选项对 2.0 的 harness 有**完全相反**的含义：

| | **Electron** | **Tauri** |
|---|---|---|
| WebView | 自带 Chromium（**三端一致**） | 系统 WebView（Windows WebView2 / macOS WKWebView，**有差异**） |
| 运行时 | **自带 Node** | Rust；**无 Node** |
| 体积 | ~150MB+ | ~10MB |
| 若 2.0 用 pi（TS）做 harness | ✅ **直接在主进程跑** | ⚠️ 需 sidecar（pi 有 standalone binary，但**Windows 构建待核实**） |
| 对我们现有前端的风险 | 低（Chromium 行为与现在一致） | **中高**：我们有 9577 行 CSS、`CustomCursor`、液态玻璃/云动画/Shimmer，WebView 差异会变成跨平台回归 |

**推荐 Electron**，三个理由：
1. 我们前端视觉资产重且依赖精确渲染，**Chromium 一致性**值这个体积；
2. 2.0 若用 pi，**Electron 自带 Node，不需要 sidecar 这层额外复杂度**；
3. 学生团队：DevTools 与调试体验更接近现状。

> 若确定 harness **永远不上桌面端**且在意体积，Tauri 更优 —— 但这个"确定"现在给不出来，所以按最可能的未来选。

**推论**：桌面端前移 = **把 harness 的位置决策从 2.0 提前到 beta**。
如果 beta 选了 Tauri 而 2.0 又要本地 harness，要么加 sidecar，要么推翻技术栈。

## 3. 两个已核实的具体缺口（若前移，需要提契约变更）

| 缺口 | 实测 | 影响 |
|---|---|---|
| **埋点没有渠道/平台维度** | `AnalyticsEvent` 只有 `id / category / eventType / sessionId / payload / occurredAt / createdAt`，**无平台或渠道字段**（`openapi.yaml` L5266） | beta 上桌面端后，**pilot 的核心指标无法按渠道切分**（#53 要求"pilot 核心指标现在就定"）。虽然 `payload` 是自由 object 可临时塞，但没有一等字段就无法可靠聚合 |
| **契约没有客户端版本协商** | 全契约搜 `clientVersion` / `X-Client` / `User-Agent` / `platform` **零命中** | 桌面端会引入「**旧客户端 + 新服务端**」这个 Web 时代不存在的兼容问题。至少需要「最低支持客户端版本」的表达方式与拒绝策略 |

> 这两条都要走 X0 评审、改 `openapi.yaml`。**现在提成本低（pilot 删档期 schema 可激进），beta 再提就要带迁移。**

## 4. 风险：真正危险的是「同时前移」

| 情形 | 风险 |
|---|---|
| 只前移壳，harness 留 2.0 | 低。工作量是打包 + 6 条约束，不碰 B 板块 |
| 壳 + harness 同时前移到 beta | **高**。B 板块（Chat 内核）是 M1 的主战场且**后端目前根本不存在**；harness 选型（pi vs 自研）会改写 `routes/chat.py` 的形状。**M1 未完成时三线并行 = M1 烂尾** |
| 前移但不做 §1 的 6 条约束 | 中。会在 beta 集中爆雷，且 SSE/存储抽象要重写 |

**最该避免的组合**：`M1 未完成` + `桌面端壳并行` + `harness 并行`。

---

## 5. 建议路径

1. **beta 只做壳，harness 留 2.0**（推荐）。
2. **现在（M1 期间）花半天做三件不改代码的事**：
   - 把 X1 定义扩成「三端壳」；
   - 把 §1 的 6 条约束写进 X1 板块契约；
   - 把 §3 的两条契约缺口提给 X0（埋点加渠道维度、加最低客户端版本表达）。
3. **若 beta 确实也要 harness**：那么 **pi vs 自研的实测（半人日）必须在 B 板块动工之前完成**，
   否则 `routes/chat.py` 会白写一遍。这条是硬前置，不能并行。
4. **把 beta 的准入标准补上桌面端条目**（#53 已建议"每阶段定准入标准"）：
   例如「桌面端安装包在三平台可启动且登录态保持」「契约变更后旧客户端有明确拒绝行为」。

## 6. 需要你决定的问题

1. **beta 上桌面端的商业理由是什么？**（留存 / 分发 / 离线 / 家长端？）
   → 这直接决定 §1 第 5 条能不能守住。若理由就是"离线可用"，那合规面要重新评估，本评估的结论要改。
2. **目标平台优先级？**（Windows 优先，还是 mac/双端）→ 影响技术栈与打包链路。
3. **是否接受「桌面端 = 壳 + 服务端一切」这个限制？**（我建议接受，见 §1 第 5 条）
4. **harness 最终在不在本地跑？** —— §2 说明这个问题已经被前移决定强行提前了。
