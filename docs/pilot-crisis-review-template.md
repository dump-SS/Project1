## 评审机制怎么跑

1. **用例集**：`backend/tests/data/crisis_cases.yaml`——正例覆盖基线 4 类触发，负例覆盖 L1 / L2 / 学习类误伤。用例 id 是评审记录的对照键，尽量不改。
2. **评测**：`cd backend && .venv\Scripts\python.exe -m pytest tests/test_crisis_response_review.py -v -s`——逐条断言，末尾输出按类召回与误报率（`-s` 才能看到汇总打印）。
3. **一致性断言**：`safety_filter.CRISIS_RESPONSE` 与 `crisis_response.txt` 的「L3 固定转介文案」逐字一致。测试从 txt 解析（文案不进测试代码），两处任一改动不同步即红。
4. **缺口挂牌**：已知召回缺口在用例集里标 `known_gap: true`，测试以 `xfail(strict=True)` 挂牌——将来扩召回使它转绿时套件变红，强制摘牌复评；缺口不允许静默消失。

### 红线的操作定义（本记录的核心结论）

**字面的「任意自然语言 100%」不可证**——任何固定检测器都追不上无穷措辞，宣称「已 100%」即是自欺（本项目反复栽过的「测试绿了冒充红线达成」正是此坑）。本记录采用的**可核查操作定义**：

1. **验证语料召回 100%**：语料是冻结产物（正例 13 覆盖 4 类 × 变体、负例 10 含 5 条边界陷阱），改语料要说明原因；
2. **误报 0**：负例全守，且**语义兜底的失败方向是 fail-toward-refer**——只在尖锐措辞（软标记）上发生，普通倾诉永不因兜底故障被误报（有专门测试守住：无软标记负例不触发兜底）；
3. **未命中留痕可复核**：每次语义兜底调用写 `ai_call_log`（场景/耗时/成功/判定理由），评审机制按此抽检——**不是黑箱**，每次「为什么这样判」都有记录；
4. **残差单列**：无软标记又无第 1 层命中的极端含蓄表达，两层都覆盖不到——**如实声明不宣称已覆盖**，作为人工抽检对象。

### 残差与边界（如实声明）

- 无软标记 + 无第 1 层模式的极端含蓄表达（如纯代称、刻意编码）仍是盲区；
- 第 2 层仅在 chat 路径启用（chat 消息本就要发给 LLM，无新增出域）；**建议路径（学习记录 note）保持第 1 层**——note 属不出域硬约束内容，为分类新增出域不可接受；
- 第 2 层的误报面 = 含软标记的正常表达（如「和这学期告别了」）：正常时由模型放行；**LLM 故障时长这类表达会被转介**（fail-toward-refer 的已知代价，已在用例集里备好这类负例供评审对照）。
